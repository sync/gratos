Gratos: Effect-native Grats

Plan v11 · for council review · 2026-11-24 · Node 26 · TypeScript 7 · Turborepo · one PR per milestone

We vendor the last TypeScript release of Grats into this repo, port it to the TypeScript 7 compiler API, and teach it to read Effect.Effect and Stream.Stream return types. We then build a small GraphQL server core with plugins, and an Effect layer that runs every resolver in the request's fiber context. The three spec diagrams (Grats: the schema comes from the code, An Effect-native GraphQL server, Plugins and resolvers) are the source of truth. This page records how we will build them, where we depart from them, and how each milestone is proven.

For the council. Score the plan out of 10, where 9 means "approve, start M0". Every claim marked verified was run on Node 26.13 against the exact versions listed. Each proposed default takes effect unless the council overrules it, so the plan has no open blockers. Please challenge the milestone order, the mechanisms, and whether the acceptance criteria can be checked.

Decisions made

Runtime
Node 26 everywhere

No Bun APIs. Effect platform-node provides FileSystem, Path and the HTTP server. Packages run from source through Node's type stripping; there is no build step.

TypeScript
TS 7 everywhere

One TypeScript, 7.0.2. tsc --noEmit typechecks each package, and Grats uses its API (typescript/unstable/sync + unstable/ast). TS 5.9.2 survives only behind Grats' facade, as a fallback and a test oracle.

Scope
All three specs, phased

The compiler, the server core with plugins, the Effect layer and an example app. The spec's "client compiler" box is out of scope.

Compiler
Vendor v0.0.36, Effect shell

The extractor, transforms and codegen keep upstream's logic, so upstream's fixture suite stays the proof. The CLI, config, file IO, the compiler-process lifecycle and errors are Effect.

graphql-js
17.1

Native @defer/@stream. graphql-jit 0.10.1 runs on 17.1 unpatched (verified).

Monorepo
pnpm + Turborepo

The generated files are committed. A task graph with a local cache, restored in CI.

Agents
One source for every agent

Skills live in .agents/skills, and .claude/skills holds symlinks to them. AGENTS.md holds the rules, and CLAUDE.md is just @AGENTS.md.

Delivery
PR per milestone, full send

Each milestone follows the user's full-send skill: prove, run sol-loop, file a PR, babysit CodeRabbit and CI, and merge once the merge gate passes. When a change is uncertain, I stop and suggest a council.

Facts that shaped the plan (all verified)

  • Upstream: grats@0.0.37 (Oct 2026) already ships the Rust binary. v0.0.36 (commit 5ab6616, Apr 2026, MIT) is the last TypeScript engine: about 11.2k lines in 55 files, 455 fixture inputs and 29 integration fixtures. Its typescript is a regular dependency pinned to 5.9.2.
  • TypeScript 7 API. typescript@7.0.2 runs the Go compiler (tsgo) as a child process. typescript/unstable/sync gives projects from a tsconfig, programs, diagnostics, a checker and emitter.printNode. unstable/ast gives node types, is* guards, a factory, a visitor, getJSDocTags and comment ranges. Spikes, with lib files loaded correctly: a project of 94 files opens in about 180 ms cold, including the process spawn. A class's @gqlType tag is read and its symbol resolved. printNode output on a schema.ts-shaped tree was byte-identical to TS 5.9.2's printer on a sample. parent, getText, getStart, getLeadingCommentRanges and NodeHandle.resolve() (identity-preserving) all work. The API's virtual-FS readFile callback can serve export {}; for third-party code files, which is the spec's §5 trick.
  • Where TS 7 differs from TS 5 (inventoried against upstream's 804 ts. references):
    • factory signatures differ: 282 calls go through 49 factory functions, and some helpers are missing (createTrue, createNull, createModifier …);
    • JSDoc comment is always a NodeArray, never a string (11 sites in Extractor.ts);
    • getChildren, getNameOfDeclaration and formatDiagnosticsWithColorAndContext are missing;
    • a few guards are renamed;
    • symbol declarations are NodeHandles;
    • programs open only from a tsconfig;
    • parseConfigFile drops the grats key;
    • the checker is called in only 3 places, and getMergedSymbol is the identity in TS 7.
    M2 is scoped around this list.
  • Effect 4.1.5 has every API the spec uses: runForkWith, Fiber.pollUnsafe/interruptUnsafe/addObserver, Exit-as-Effect, Cause.findError/hasInterruptsOnly/squash/pretty, Stream.toAsyncIterableWith, Effect.withFiber, Match.tagsExhaustive, effect/http HttpRouter. Two corrections to the spec: a span cannot be renamed, and the only way to backdate one is the Tracer.Tracer service's own method, Context.get(fiber.context, Tracer.Tracer).span({ name, parent: Option<AnySpan>, annotations, links, startTime, kind, root, sampled }). There is no module-level Tracer.span. M5's tracing design follows from that.
  • graphql 17.1: plain execute() throws on any schema that contains @defer/@stream. The incremental executors are experimentalExecuteIncrementally (pending/incremental/completed) and legacyExecuteIncrementally (the deferSpec=20220824 shape). abortSignal and hideSuggestions are execution options. M4's design follows from this.
  • Node 26 strips types in workspace packages because it resolves realpaths through pnpm symlinks. --preserve-symlinks breaks that with ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING. TS 7 tsc -b with project references needs emit (TS6310), so we use per-package tsc --noEmit.

  • Generated files are committed (src/generated/*), as the grats skill and the spec ask. codegen:check runs gratos --check: it writes nothing and exits 1 if the committed files are stale. check never runs codegen, so there is no write/check race. pnpm codegen is a developer task.
  • transit has no script. It exists so that a change in @dblechoc/gratos or @dblechoc/gratos-server source invalidates dependents' codegen:check, typecheck and test hashes. $TURBO_DEFAULT$ keeps vitest.config.ts and tsconfig files in the hash.
  • The root scripts never recurse. The root package.json scripts are "lint": "oxlint .", "fmt:check": "oxfmt --check .", "check": "turbo run check" and "codegen": "turbo run codegen". The //#lint and //#fmt:check root tasks run those direct commands. A root script that called turbo run lint would recurse: turbo reports recursive_turbo_invocations (verified). Root files that packages consume (tsconfig.base.json, vitest.shared.ts) are listed as $TURBO_ROOT$/… inputs on the package tasks. A package's default inputs stop at its own folder, so without these a root edit would leave package hashes unchanged (verified). globalDependencies also covers them, as a second layer.
  • There is no build task and no project references. Each package's typecheck is tsc --noEmit (TS 7), and cross-package types resolve through exports that point at .ts files (verified). Keys are checked against the docs bundled with turbo 2.11.13.

Delivery workflow (the full-send skill)

branch off main→ implement + prove
turbo run check + milestone proof→ sol-loop→ file-pr→ babysit-pr
CodeRabbit + CI→ merge gate passes → merge → next milestone from updated main
  • Each milestone is one PR against main. It contains the acceptance checklist and the proof: command output, benchmark numbers and parity diff counts.
  • CodeRabbit is "clean" when all of these hold:
    • (a) its check for the current head SHA has completed;
    • (b) no coderabbitai[bot] review thread is unresolved (GraphQL reviewThreads.isResolved);
    • (c) every nitpick, outside-diff and additional comment in the review body has a reply, either fixed or declined with a reason;
    • (d) the check run named ci has concluded success on the head SHA, and every other required check is green;
    • (e) the branch is up to date and mergeable.
    There are at most 5 fix rounds. A finding I declined that is raised again gets one more reply and then counts as answered. If findings are still open after 5 rounds, I stop, leave the PR unmerged, and ask you.
  • When CodeRabbit does not respond: if no review arrives 15 minutes after a push, I comment @coderabbitai review once. If there is still none after 30 minutes, or it reports being rate-limited, paused or skipped, I stop and report.
  • Merge (full send). The gate is evaluated against one recorded PR head SHA. The proof, a successful ci and a completed CodeRabbit review must all be for that SHA. The merge call pins it: gh pr merge --squash --match-head-commit <sha>, which is the REST sha parameter. If the head has moved, the merge is refused, and the gate is re-evaluated on the new head. When the merge gate passes, I squash-merge the PR (the repository allows all three methods and has no history to copy, so the method is fixed here). The gate requires: proof covers every change in the diff; the check run named ci has concluded success on the PR's head SHA, and every other required check is green; CodeRabbit is clean as defined above; no human review requests changes, and no human review thread is unresolved (including on COMMENTED reviews); the branch is up to date and mergeable. Milestone proof that CI does not run, such as clean-clone FULL TURBO, verify-vendor, cold-build and RSS numbers, or the ≤ 2 s restart, is re-run on the final head SHA whenever a babysit fix touched relevant code. I never use --admin or any other bypass of branch protection. The final report gives the PR link, the merge commit, the proof and every decision made. Before the next milestone branches from the updated main, I confirm that ci on the merge commit is green. A red main stops the chain, and I ask you. There are no stacked PRs.
  • When unsure, suggest a council. If a milestone hits a change I can't prove or am not confident in, I stop before merging and ask you through the question tool, recommending a council review. Examples: a departure from the spec that this plan doesn't list, a design choice the plan leaves open, a failed acceptance criterion, or the M2 escape hatch. A council then reviews that change under the same ≥ 9/10 rule.
  • Asking follows full-send's rules. Questions go through the question tool with the PR link and a recommended option. Data deletion, production changes or changes outside the repo always ask first.

M2Port the engine to TypeScript 7PR 4 · feat/grats-ts7
  • src/ts/ is a TS5-shaped facade with two implementations. The TS 7 port is the only one the CLI and dev step ever load. The TS 5.9.2 pass-through is a devDependency used only by the parity harness, so the same engine is diffed on both TypeScripts. Upstream modules change their import line, plus a listed set of call sites that are routed through facade helpers working on both TypeScripts: tag.comment reads, symbol.declarations, node.getChildren and so on. That way parity bar (b) runs the same code on both. The TS 7 implementation:
    • owns the API process as an Effect resource (acquireRelease: new API(...) / api.close());
    • provides TS5 factory signatures, with the missing helpers built from existing nodes;
    • flattens JSDoc comment NodeArrays to strings;
    • replaces getChildren by rewriting comments.ts on the scanner;
    • adds getNameOfDeclaration and the renamed guards;
    • resolves NodeHandles;
    • makes getMergedSymbol the identity;
    • ports formatDiagnosticsWithColorAndContext byte for byte, because 211 snapshots depend on it;
    • adds printList on top of emitter.printNode, which wraps printer panics as a typed defect;
    • adds a minimal createSourceFile (a line map only), which DiagnosticError and TSAstBuilder need. It is not exported by unstable/ast;
    • imports the factory from typescript/unstable/ast/factory, and always passes arrays (never undefined) for typeArguments, because TS 7's createCallExpression throws otherwise (verified).
  • Config: parseConfigFile drops unknown keys, so generate() reads the root tsconfig through FileSystem, parses it with jsonc-parser (comments and trailing commas), and takes the top-level grats key from the root file only, with no extends merging, as TS 5's raw did. It decodes that with Schema, and takes fileNames/options from the API.
  • Fixture harness: each fixture gets a virtual tsconfig with explicit compilerOptions (2.3 ms per fixture, measured). Supported options on TS 7: target ≥ ES2015, with the pair module: "nodenext" + moduleResolution: "nodenext" or module: "preserve" + moduleResolution: "bundler" (there is no module: "bundler"), and strict as each fixture sets it. TS 7 rejects target: ES5 and moduleResolution: node10. Fixtures that depend on those, on TS 5's {} defaults, on tsVersion gates, or on the TS1005 message get one variant per TS version, and every such difference is listed in the PR.

The first executor returned is the one called, and only after every hook and the gate step passed. An executor receives next, which runs the next claim in list order or else the default executor, so jit() counts and compiles only operations that nothing refused. The spec's serverTiming example replaces the Response the same way.

      • Its cancel(reason) ends the span with cancel and forwards the cancel to the original body. pull checks the same ended flag before touching the controller, because a pending read() resolves done after a cancel, and closing the cancelled controller would throw.
      • This works for a single JSON body and for SSE and multipart bodies alike, so the span ends after the last payload is written.
      • (Amended during M5 review.) Once the core has ended a streamed response itself (its closing frame, event: complete or the close delimiter, is in the body, after a failed source's error payload too), a client that leaves before reading the end (an abort, a body cancel, the request Scope closing) keeps the stream's outcome: ok, or error for a failed source, never cancel. The core records that end per request (internal request state the Effect layer reads).
      Backstop: effectRoute registers the same finalizer with the HTTP request's Scope (Effect.addFinalizer). That scope closes after the transport has finished with the response: after the body is written, after a discarded body such as a HEAD response (which is neither read nor cancelled, verified), after a transport failure, or after an interrupt. This was verified on Effect 4.1.5's NodeHttpServer: the route has a request Scope, which closed 8 ms after a streamed body's close, immediately after a HEAD response, and 4 ms after a client cancel. It does not use Effect.ensuring or an onExit on the route fiber, which ends at time-to-first-byte. The body wrapper gives the exact end time. (Amended during M5 review: for HEAD, effectRoute now cancels the Web body itself and answers with no body, so a HEAD response ends through the body's cancel as well as through the scope backstop.)
      • Closed flag: the per-request finalizer state has a closed flag. The finalizer sets it, and ends any span that exists with cancel. For a mutation that the core reports as started, which keeps running after the client leaves, the end is deferred until the core's tracked mutation promise settles. The status is then ok or error, not cancel. The deferral depends only on that started signal, never on onContext's mutation mark alone. If the core skips the mutation under the no-late-start check, it reports the request as not started, and the deferred end resolves at once with cancel. A span created after closed is set, in onContext or as the early-exit span in onResponse, is ended immediately with cancel. This covers a client that leaves while the context factory is still running: the scope closes before the span exists (verified, scope closed at 114 ms, span would be created at 415 ms).
      • No body: if res.body === null in onResponse (for example the 499 abort response, or a 204), effect() ends the span there and returns the Response unchanged. A null body has nothing to wrap, and a 204 with a stream throws.
      • A second call does nothing.
      • (Amended during M5 review.) A cancel, or a streamed body that fails (a throwing onResult hook, a payload that cannot be serialized: the core stops the executor then), is recorded when the finalizer decides it, but the span itself ends once the request's Effect work has settled: every fiber the request scope tracks has exited (an interrupted resolver after its finalizers) and every Stream source it pulled has closed its scope (return() on its iterator), never before the latest child span end. The transport is not held: the response is over for it already. A started mutation never ends with cancel, so it never waits here, and its end still comes before drain() resolves.
      Together these three triggers (body wrapper, null body, request scope with closed flag) guarantee an end under effectRoute. For a standalone handle(Request) with no scope, they guarantee an end provided the caller consumes or cancels the body. The core sends GET and HEAD 405s with a null body, so those go through the null-body path.

With that rule, plugin order does not matter. Both [serverTiming(), effect()] and the spec's [effect(), serverTiming()] end the span correctly (verified).
  • Context and guard. runInRequest(request, effect, services) runs an Effect inside the context factory, and its span shares the request's trace. makeGuard({ authorize, flags, timeout = 60 s, headers }) provides ctx.guard and ctx.guardStream.
    • A refusal returns Effect.fail(refuse()), where refuse builds the app's own error, such as Forbidden in the spec's union. That value is an Exit, so it costs no fiber and no span.
    • The timeout applies to queries only. A mutation gets no interrupting timeout. guardStream times out only the setup effect, never the stream itself.
    • The timeout is a defect, not a typed failure. A timeout dies with the library's GuardTimeout, so resolver types stay Effect<A, AppError, R>. If it were a typed failure, the app's Match.tagsExhaustive would throw absurd on it (verified). fromCause checks the defects for GuardTimeout before the ResolverDefect fallback, and maps it to gqlError("Request timeout", 504), which can be overridden with effectSchema({ onTimeout }).

With no server, as in unit tests, it defaults to "query", and a test can set it. (Amended during M5 review: a resolver that runs with no request scope, a bare server say, gets the type of its own operation from info.operation, so a mutation never gets the query timeout; the "query" default applies only to an Effect run outside the wrapper.)

Council implementation notes (non-blocking, recorded after approval)

All three council members approved plan v11 at 9/10. These are the non-blocking notes from the approving round. They are applied in the milestone named, checked by that milestone's proof and review, and change none of the approved mechanisms, scope or delivery process. If one of them turns out to change a mechanism, the full-send rule applies: stop and suggest a council.

  1. M4a, one gate step: the drain-gate check, the no-late-start check and registration in the tracked set run in one synchronous step just before the executor call, so every mutation is either tracked or never started. Test: shutdown while a mutation is in a slow runInRequest context factory ends either with zero executor calls and a cancel span, or with both fields committed before any service is released.
  2. M4a, core export: mutationOf(req): { started: Promise<boolean>, settled: Promise<void> } | undefined, alongside signalOf and startOf. started resolves false on every path that never calls the executor. The started signal is published, and the completion promise registered, before the executor is called. The operation span is ended before that promise settles, so the drain waits for both.
  3. M4a, refusal while draining: a mutation refused during the drain gets a 503 with extensions.code: "SERVER_DRAINING", with a test. warnAfterMs logs once when the threshold passes, then again every warnAfterMs while the drain is blocked.
  4. M5, teardown wording: the plan relies only on the drain and the mutation span end happening before the tracer and services are released. The release order between the tracer and the services depends on the Layer.provide order and is not relied on.
  5. M5, the shutdown test under NodeHttpServer: HttpRouter.serve's graceful-shutdown wait runs before the drain finalizer. The regression test therefore aborts the client socket, or sets a short gracefulShutdownTimeout or disablePreemptiveShutdown, so that drain really runs while the mutation is held. The test's "a warning is logged" assertion catches a misconfiguration.
  6. M5, ordering inside the drain: the span-end continuation is registered when the mutation starts, or drain() yields a microtask after its tracked promises settle, so a direct control.drain() call in a unit test keeps "span end before drain done".
  7. Prose: the "9 of 500 trials" figure in the Clock note came from separate reads. A re-run gives 0 of 500 on the default hrtime Clock and 495 of 500 on an ms-quantized Clock without the anchor, and 0 of 500 with the anchor in both cases.
